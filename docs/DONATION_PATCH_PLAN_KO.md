# LambLink 후원 수신·이벤트 처리 패치 계획서

작성일: 2026-09-10
상태: 수신·진단·저장·표시 코드 구현 및 자동 검증 완료. 실환경 검증과 배포는 미완료. [구현·검증 기록](DONATION_PATCH_VALIDATION_KO.md) 참조.
대상: Companion의 치지직 후원 수신부터 Mod의 효과 적용, 결과 확인 및 오버레이 표시까지.

## 1. 목적과 완료 기준

후원 신호가 들어오면 정상 처리하거나, 처리하지 못한 이유를 남긴다. 스트리머가 오버레이를 보지 못했더라도 다음을 확인할 수 있어야 한다.

- 후원 신호를 받았는가?
- 금액과 후원자 정보를 해석했는가?
- 이벤트 대상이었는가? 제외했다면 이유는 무엇인가?
- 게임 전달을 기다리는가, 게임 내 적용을 기다리는가?
- 실제 효과가 적용됐는가? 어떤 효과였는가?
- 오버레이 표시를 요청했는가, 연결된 페이지에서 표시 처리를 확인했는가?

수신, 게임 적용, 화면 표시를 각각 판정한다. `DONATION_READY=True`나 웹소켓 연결만으로 후원 성공을 판정하지 않는다. 브라우저의 표시 확인도 OBS의 실제 방송 출력·소스 가림 여부를 보증하지 않는다.

## 2. 장애 근거와 현재 구현

### 확인된 사실

9월 9일 Companion 로그에는 후원 구독 완료 후 DONATION 신호가 3건 기록되어 있다. 세 건 모두 바로 `DONATION parse failed`로 끝났다.

| 신호 | 수신 로그 행 | 실패 로그 행 | 데이터 크기 |
|---|---:|---:|---:|
| 1 | 2211 | 2212 | 274바이트 |
| 2 | 3125 | 3126 | 326바이트 |
| 3 | 3230 | 3231 | 270바이트 |

자료: `C:/Users/sjnote/Documents/카카오톡 받은 파일/companion-1.0.0.log`, `LogOutput.log`.

현재 수신 코드는 역직렬화에 실패하면 후원 콜백을 호출하지 않는다. 따라서 이 3건은 금액별 규칙 결정, 영속 대기열 저장, 게임 전달에 도달하지 못했다. 게임 로그에도 대응하는 적용 결과가 없다. 9월 2일의 오버레이 정상 접속 기록과 혼합하지 않는다.

### 추가 조사 후 원인 판단 (2026-09-10)

현재 [치지직 Session 공식 문서](https://chzzk.gitbook.io/chzzk/chzzk-api/session#message-event-subscribe-donation)는 `payAmount`를 문자열로 설명하지만, [공식 Session API의 개발자 실측 기록](https://gist.github.com/fi-xz/69ce1f35ca1b2318a2b410c0d5757e0f#donation)은 일반·영상 후원에서 JSON 숫자로 전달됨을 명시한다. 이는 네이버의 공식 정정 공지가 아니라 직접 연결한 개발자의 관측 자료다.

현재 LambLink 빌드의 실제 `DeserializeEventPayload<DonationEvent>`를 .NET 8.0.30에서 호출해 비교한 결과, 문자열 `"1000"`은 성공하고 숫자 `1000`은 null을 반환했다. 내부 예외는 `JsonException`, 필드 경로는 `$.payAmount`, 이유는 숫자 토큰을 문자열로 읽을 수 없다는 것이었다. CHAT와 VIDEO 모두 같은 결과다.

따라서 **숫자 금액을 처리하지 못하는 구현 결함은 재현으로 확인했고, 9월 9일 장애의 가장 유력한 원인으로 판단한다.** 다만 당시 세 건의 원문과 필드별 예외가 없어 그 세 건의 직접 원인까지 확정한 것은 아니다. 숫자·문자열 금액 동시 지원은 추가 원문 확보를 기다릴 필요 없이 P0 수정 대상으로 진행한다. 자세한 근거와 한계는 [추가 조사 기록](DONATION_AMOUNT_RESEARCH_KO.md)에 정리했다.

후원 금액·닉네임·메시지, 실제 결제인지 테스트 알림인지도 기존 로그로 복원할 수 없다. 과거 세 건을 임의의 금액으로 자동 재실행하지 않는다.

## 3. 패치 우선순위

P0는 후원 수신을 정상화하기 위한 필수 수정, P1은 운영 배포 전 완료할 신뢰성·검증 작업이다. 검증 항목은 문제가 재현되지 않으면 기존 구현을 유지한다.

| 순서 | 우선순위 | 작업 | 완료 판단 |
|---|---|---|---|
| 1 | P0 | 실패 진단·수신 추적 추가 | 실패 필드·자료형·원인을 추적할 수 있음 |
| 2 | P0 | 후원 전용 파서와 입력 정규화 | 허용된 실제 형식은 처리하고 잘못된 금액은 명확히 거부 |
| 3 | P1 | 단계별 상태·최근 결과 조회 | 화면 없이도 후원별 진행·실패를 확인 |
| 4 | P1 | 영속 저장·재전송·중복 적용 보완 | 중단·저장 오류 시 조용한 누락이나 중복 적용 없음 |
| 5 | P1 | 금액·지역·효과·일시정지 검증 | 규칙과 실게임 변경이 일치 |
| 6 | P1 | 오버레이 표시 결과 추적·복구 통합 | 적용 성공과 표시 여부가 별도로 확인됨 |
| 7 | P1 | 실제 치지직→게임→OBS 통합 검증 | 실제 수신 형식으로 끝까지 통과한 증거 확보 |

## 4. 상세 작업

### 4.1 수신 실패를 진단 가능한 상태로 만들기

수정 대상: `Chzzk/ChzzkRealtimeClient.cs`, 진단 관련 클래스.

- DONATION 프레임을 인식한 시점에 실행 세션 ID와 수신 순번을 부여한다. 후원 요청 ID는 정상화 이후 연결하고, 파싱에 실패해도 추적 ID가 남게 한다.
- 후원 관련 단계 로그에 UTC 시각을 추가한다. 시작 시각만으로 이벤트 시각을 추정하지 않도록 한다.
- 범용 파서의 `catch { return default; }`에 의존하지 않고 실패 이유를 반환한다. 예: JSON 형식 오류, 잘못된 루트, 누락 필수 필드, 금액 자료형 오류, 범위 초과.
- 예외 종류, 안전한 필드 경로, 알려진 필드의 존재 여부·JSON 자료형·길이, 바이트 수를 기록한다. 예외 메시지나 원문 전체를 그대로 남기지 않는다.
- 필드 이름은 허용 목록으로 제한하고 알 수 없는 필드는 개수 등 구조만 기록한다. 실패 진단과 지원 ZIP에 닉네임·후원 메시지·인증 토큰·원본 식별자가 새로 노출되지 않도록 검증한다.
- 한 건이 잘못되어도 다음 후원·채팅을 처리한다. 바깥 Socket.IO 봉투 해석 오류도 원인을 구분하되, 연결 자체의 오류는 기존 재접속 감독 흐름으로 처리한다.

완료 기준: 실패한 후원과 다음 정상 후원을 연속 입력했을 때 실패 원인이 남고 정상 후원은 처리된다. 후원 원문이 없는 과거 장애에 대해서는 확정할 수 없는 범위를 유지한다.

### 4.2 후원 전용 입력 정규화

수정 대상: `Chzzk/Models.cs`, 신규 후원 전용 파서, 수신 콜백 연결부.

- 금액은 JSON 문자열 `"1000"`과 JSON 정수 `1000`을 같은 양의 정수로 정규화한다. 숫자를 무조건 문자열로 바꾸는 범용 완화 대신 금액 필드에만 적용한다.
- 음수, 0, 빈 문자열, null, 불리언, 배열·객체, 소수 및 정수 범위 초과를 거부한다. 반올림·잘라내기·기본 금액 대입을 하지 않는다. 쉼표·통화기호·지수 표기 허용 여부도 테스트로 고정하고 임의로 금액을 추정하지 않는다.
- 현재 지원하는 이벤트 객체·문자열 JSON 및 `data` 객체 포장을 테스트로 보존한다. `data` 문자열 등 추가 포장은 실제 관측된 형식에 한해 깊이·크기 제한을 두고 지원한다.
- 채널 ID 누락·불일치는 거부한다. 익명 후원에 대비하여 후원자 ID·닉네임·메시지 누락이 정상 금액의 후원 전체를 버리는 이유가 되지 않도록 한다. 이름은 표시용 기본값을 사용하며 없는 ID를 만들어내지 않는다.
- `donationType`의 CHAT·VIDEO를 검증한다. 미지원 종류는 사유와 함께 제외하며, 원문에 검증 가능한 표지가 없는 한 테스트 알림/실결제를 추측해 구분하지 않는다.
- 채팅·구독 역직렬화 동작은 유지하고 관련 회귀 테스트를 추가한다.

완료 기준: 동일 금액의 문자열·숫자 입력이 같은 규칙 구간에 도달한다. 필수 정보가 잘못되면 게임 명령을 만들지 않는다. 정상 후원자 정보는 표시 단계까지 보존된다.

### 4.3 후원별 상태와 최근 결과 조회

수정 대상: Companion 진단·추적 클래스, `Program.cs`, 필요 시 제한된 처리 이력 저장소.

다음 상태를 구별하고 내부 요청 ID로 연결한다.

`수신 → 해석 완료 → 대상 판정 → 저장 완료 → 전달/적용 대기 → 적용 성공·실패·결과 불확실`

해석 실패·대상 제외는 별도 종료 결과다. 표시 상태는 게임 처리 상태와 별도로 `표시 대기 / 페이지 표시 확인 / 미연결 / 만료`로 관리한다.

- `status`에 수신 수, 해석 성공·실패 수, 제외 수, 대기 수, 적용 성공·실패·불확실 수, 마지막 오류를 요약한다. 누적 건수와 현재 대기 건수를 구별하고 재전송 횟수를 새 후원 건수로 세지 않는다.
- `donation status`, `donation recent` 등의 조회 명령을 추가한다. 최근 결과에는 시각, 금액, 효과명, 처리 단계, 사유를 제공하되 후원 메시지 원문은 보존하지 않는다.
- 현재 성공/종료 시 발신 대기열에서 삭제되는 기록과 별도로 제한된 최근 결과를 유지한다. 보존 개수·기간·정리 규칙을 정의하고 기존 사용자 데이터와 분리한다.
- 후원 이벤트 비활성화, 최소 금액 미달, 해당 규칙 없음은 오류가 아니라 명시적인 제외 사유로 남긴다.

완료 기준: 오버레이를 닫은 채 테스트해도 수신부터 적용 결과까지 후원별로 확인할 수 있다.

### 4.4 영속 저장·재전송·중복 적용의 신뢰성

수정 대상: `Storage/DonationDeliveryRepository.cs`, Mod `DonationReceiptStore.cs`, 양쪽 `Program.cs`/`Plugin.cs`.

현재 저장소는 메모리 목록을 변경한 뒤 파일에 저장한다. 저장 예외가 발생하면 메모리와 디스크 상태가 달라질 수 있다. 이는 이번 로그의 직접 원인은 아니지만 장애 주입 테스트로 확인하고 보완해야 할 코드 경로다.

- 추가·시도 기록·완료 처리의 상태를 복사한 후 저장 성공 시 확정하거나, 실패 시 변경을 되돌리는 구조를 적용한다.
- 저장 실패를 성공 수신·완료로 보고하지 않는다. 기존 정상 파일을 보존하고, 재시도 가능/불가능 상태와 운영자 확인 필요 상태를 구별한다.
- 손상 파일을 격리한 뒤 빈 대기열·빈 영수증으로 재개하는 현 동작을 점검한다. 특히 Mod 영수증 손상으로 중복 여부를 모르면 해당 후원의 자동 재실행을 막고 복구 필요 상태를 표시한다.
- 기존 내부 `RequestId`는 재전송·Companion 재시작에서도 유지한다. ACK 유실, 중복 결과, 재연결 시 같은 요청이 게임 효과를 다시 적용하지 않도록 한다.
- 적용 도중 게임이 종료되어 결과를 알 수 없는 기존 `UNCERTAIN` 정책을 유지하고 사용자 조회에서도 분명히 표시한다. 실제 게임 저장까지 원자적으로 보장하는 것처럼 설명하지 않는다.
- 외부 치지직 이벤트 재전달은 별도 문제다. 검증된 고유 이벤트 ID가 제공될 때만 이를 활용한다. 닉네임·금액·짧은 시간 간격만으로 서로 다른 정상 후원을 제거하지 않는다.
- Mod 완료 영수증 보존 한도 2,048건과 Companion 대기열 한도 5,000건의 상호작용, 장기 ACK 유실 이후 재전송을 검증한다. 무제한 기간의 ‘정확히 한 번’을 주장하지 않으며, 보존 밖 요청은 안전한 정책을 먼저 정한 뒤 처리한다.

완료 기준: 쓰기 실패·권한 오류·손상 파일·프로세스 재시작·중복 요청 시 누락/중복/불확실 상태가 테스트의 기대값과 일치한다.

### 4.5 금액별 규칙과 실제 게임 효과 검증

수정/검증 대상: `Rules/DonationRuleEngine.cs`, Mod `DonationEffectService.cs`, `DonationGameplayGate.cs`, `DungeonDonationBuffs.cs`, `Plugin.cs`.

- 기본 규칙의 1,000 / 3,000 / 5,000 / 10,000원 경계를 검증한다. 커스텀 설정을 기본값으로 덮어쓰지 않고 잘못된 구간·빈 이벤트 풀·지원하지 않는 효과의 판정을 명확히 한다.
- 마을과 던전의 허용 효과가 각각 선택되는지 검증한다. 랜덤 결과는 테스트에서 고정하거나 지정하여 모든 효과 분기를 확인한다.
- 로딩 중 수신 후 다른 지역으로 이동한 경우 Mod가 실제 적용 지역으로 보정하고, ACK와 오버레이가 최종 효과명을 사용하는지 확인한다.
- 로딩·컷신·대화·일시정지 중 효과 적용과 지속시간이 멈추고 플레이 재개 시 이어지는지 확인한다. 정상 대기를 오류나 누락으로 표시하지 않는다.
- 체력·신앙·포만도·열정·공격력·이동속도·적 피해의 적용 전후 값을 검증한다. 함수 호출 성공만으로 실제 값 변경을 증명하지 않는다.
- 최대 체력·대상 신도 없음·적 없음 등 효과가 변화를 만들 수 없는 상황은 정상 무변화인지 실패인지 효과별 정책을 명시한다.
- 연속 후원, 같은 버프 중첩 대기, 추첨과 동시 발생, 던전 종료와 저장 파일 전환을 회귀 검증한다. 대기 후원이 어느 저장 파일에 적용되는지는 기존 정책을 확인하고 테스트로 고정한다.

완료 기준: 각 효과의 성공·실패·정상 무변화 결과가 실제 게임 상태와 일치하고, Mod 결과에 최종 지역·효과·검증 가능한 상세가 남는다.

### 4.6 적용 성공과 오버레이 표시를 분리

수정 대상: 프로토콜/Companion 결과 추적, `RaffleOverlayServer.cs`, 로컬 연결 파일 연계.

- 게임 적용 성공 ACK 후 카드를 표시하는 기존 순서를 유지한다. 미적용 후원을 ‘이벤트 발동’으로 표시하지 않는다.
- 카드에 내부 요청 ID 또는 별도 표시 ID를 연결한다. 클라이언트가 해당 카드를 표시 처리했을 때 ID·문서 버전·클라이언트 세션으로 확인을 돌려준다. 동일 카드 확인이 중복되어도 게임을 다시 적용하지 않는다.
- 현재 자동 복구용 heartbeat는 페이지의 응답·렌더 처리 확인이며 개별 후원 카드 표시 증거가 아니다. 후원 표시 확인은 카드가 활성 상태인 경우에만 별도로 기록한다.
- 클라이언트가 미연결인 동안 성공 카드가 조용히 소진되지 않도록 표시 대기 정책을 추가한다. 재연결 시 이미 적용된 결과 안내를 표시하고 게임 효과를 재실행하지 않는다. 대기 개수·보존시간 한도와 만료 사유를 둔다.
- 추첨 중 후원 표시 대기, 카드 순서, 실제 버프 남은 시간과 표시 시간의 차이를 검증한다. 재연결로 게임 버프가 다시 시작되거나 연장되지 않아야 한다.
- 브라우저 연결과 실제 OBS 송출 여부는 구별한다. 테스트 중 일반 브라우저를 닫고 OBS 단독 검증을 진행한다.

완료 기준: 적용 성공인데 화면이 없었던 후원을 `게임 적용 성공 / 표시 미확인`으로 조회할 수 있으며, 복구 후 안내만 한 번 처리된다.

## 5. 테스트 계획

| 단계 | 주요 사례 | 합격 기준 |
|---|---|---|
| 파서 단위 테스트 | 숫자/문자열 금액, null·잘못된 타입·소수·범위 초과, 익명, CHAT/VIDEO, 이벤트 포장 | 정상화 또는 정확한 거부 사유; 다음 이벤트 계속 처리 |
| 금액 경계 | 0, 1, 999, 1000, 2999, 3000, 4999, 5000, 9999, 10000, 정수 상한·초과 | 파서 검증과 이벤트 대상 판정이 분리되고 구간 일치 |
| 저장/전달 | 게임 미실행, 재연결, ACK 유실·중복, Companion 재시작, 파일 쓰기 실패·손상, 대기열 한도 | 보존/재시도/실패/불확실이 명확하며 중복 적용 없음 |
| 실게임 | 마을·던전 전체 효과, 최대/최소 상태, 로딩·대화·일시정지·지역 이동 | 실제 값과 결과 로그 일치 |
| 표시 | 오버레이 미연결, OBS 먼저 실행, Companion 재시작, 연속 카드, 추첨 동시 진행 | 자동 복구, 표시 확인, 순서 보존, 게임 효과 재적용 없음 |
| 실제 치지직 연동 | 실제 수신 형식의 검증 가능한 테스트 알림, 필요 시 명시적으로 승인된 실후원 | 수신 ID부터 적용·표시까지 연결된 증거 확보 |

실후원은 결제가 수반되므로 계획서 작성이나 코드 구현만으로 실행하지 않는다. 개발용 후원 명령은 치지직 파서를 우회하므로 그것만 통과해서는 실제 수신 패치가 검증된 것이 아니다. 실제 형식의 테스트 알림을 확보할 수 없으면 해당 검증을 미완료로 명시한다.

자동 테스트에서는 원문 구조와 자료형을 유지한 비식별 fixture를 사용한다. 과거 세 건의 원문은 없으므로 이를 정확히 재현했다고 주장하지 않는다.

## 6. 구현·배포 순서와 산출물

1. **진단과 파서:** 실패 결과 모델, 후원 전용 파서, 입력 fixture와 단위 테스트. 공개 실측 형식에서 재현된 숫자 금액 실패를 먼저 수정하고, 스트리머 실제 수신 형식과 실패 위치를 추가 검증한다.
2. **상태와 저장:** 수신~적용 추적, 최근 결과 조회, 저장 실패의 일관성, 중복·재시작 테스트.
3. **게임 검증:** 금액·지역·각 효과·일시정지 검증. 재현된 결함만 수정하고 기존 규칙과 사용자 설정을 보존한다.
4. **표시 통합:** 후원 카드별 표시 확인, 미연결 표시 대기, 로컬 파일 자동 복구와 실제 OBS 검증.
5. **릴리스 후보:** Companion/Mod 버전 및 필요 시 프로토콜·저장 스키마 버전 갱신, 호환성·마이그레이션·지원 로그 확인, 설치 패키지 검증 보고서 작성.

각 단계는 변경 내역과 검증 결과를 독립적으로 남긴다. Mod/프로토콜 변경이 불필요한 파서 수정은 Companion에 국한한다. 저장 형식 변경 시 기존 파일을 백업하고, 구버전으로 되돌렸을 때 대기 후원이 중복 실행되지 않는 절차를 검증한다. 릴리스 공개는 구현·테스트 완료와 별도 단계로 취급한다.

최종 산출물은 패치 코드, 비식별 재현 fixture, 자동 테스트, 실게임·OBS 검증 기록, 사용자 안내, 릴리스 노트다. 완료되지 않은 검증을 통과로 기록하지 않는다.

## 7. 배포 판정

- 지원하는 실제 후원 입력이 파싱에 성공하며, 실패 입력도 추적 가능한 결과를 남긴다.
- 모든 정상 수신 건이 제외·대기·성공·실패·불확실 중 하나로 설명된다.
- 동일 내부 요청의 재전송이 추가 게임 효과를 만들지 않는다.
- 게임 적용 결과와 후원 카드 내용이 일치한다.
- OBS 실행 순서와 Companion 재시작을 실제 OBS에서 검증한다.
- 지원 로그의 개인정보 제거와 기존 대기열·설정 호환성을 확인한다.
- 실제 치지직 수신 검증의 수행 여부를 릴리스 문서에 명시한다.

금액 자료형 수정만으로 완료 처리하지 않는다. 수신 정상화와 게임 적용·표시 검증이 모두 확보되어야 이번 후원 장애 대응을 완료한 것으로 판단한다.
