# RC35 배포 전 테스트 체크리스트

작성일: 2026-08-28

대상: `1.0.0-rc35`, Windows x64, Steam판 Cult of the Lamb, BepInEx 5.4.21, COTL_API 0.3.4

## 현재 자동 검증 결과

- 공식 `build-distribution.ps1` 전체 성공
- Mod Release 빌드: 경고 0, 오류 0
- Companion Release 빌드: 경고 0, 오류 0
- Companion/설치기 파일 버전: `1.0.0.35`
- Mod 빌드 태그: `rc35-durable-donation-delivery`
- BepInEx 5.4.21 및 COTL_API 0.3.4 공식 다운로드 SHA-256 확인
- 설치 매니페스트의 버전, URL, 구성요소 SHA-256 확인
- 최종 `SHA256SUMS.txt` 재검증 완료
- Release Companion에 개발 후원 명령, 로컬 AWS CLI/SSO 코드가 없음을 확인
- 배포 폴더에 설정, OAuth 토큰, 신도 데이터, 후원 outbox/receipt, PDB가 없음을 확인
- 저장소에서 자동 테스트 프로젝트는 발견되지 않음
- 설치기와 Companion은 Authenticode 서명이 없는 상태임

자동 빌드 성공은 게임 실행, 실시간 CHZZK 후원, 저장 호환성, 웹 배포를 증명하지 않는다. 아래 P0 항목을 실제 환경에서 통과하기 전에는 외부 배포를 승인하지 않는다.

## P0 — 배포 차단 테스트

### 1. 설치 및 실행

- [ ] 테스트 CDN 또는 스테이징 경로에 `CDN-UPLOAD` 4개 파일을 올리고 매니페스트 URL을 확인한다.
- [ ] Windows 10/11 x64 클린 PC에서 설치 EXE를 실행한다.
- [ ] Steam 라이브러리가 C:, D:, E:에 있는 경우 각각 게임 경로를 찾는지 확인한다.
- [ ] BepInEx/COTL_API 미설치 상태와 기존 설치 상태를 각각 시험한다.
- [ ] 이전 RC에서 덮어쓰기 설치 후 `%LOCALAPPDATA%\ChzzkOfTheLamb` 사용자 데이터가 보존되는지 확인한다.
- [ ] 게임 먼저 실행/Companion 먼저 실행 순서를 각각 시험하고 크래시·오류 반복 로그가 없는지 확인한다.
- [ ] BepInEx 로그에 `[BUILD=rc35-durable-donation-delivery]`가 출력되는지 확인한다.
- [ ] Companion 첫 화면과 파일 버전이 `1.0.0-rc35`/`1.0.0.35`인지 확인한다.
- [ ] 코드 서명 부재로 발생할 수 있는 SmartScreen/백신 경고를 배포 정책상 허용할지 결정한다.

### 2. CHZZK 로그인·Scope·실시간 연결

- [ ] 후원 조회 Scope를 추가한 뒤 발급된 토큰인지 확인한다. 기존 토큰이면 로그아웃 후 다시 로그인한다.
- [ ] 로그에서 `SYSTEM subscribed: event=DONATION`과 `realtime READY: CHAT / DONATION / SUBSCRIPTION confirmed.`를 확인한다.
- [ ] 401/403, 토큰 만료, 네트워크 단절 후 재로그인·재연결이 되는지 확인한다.
- [ ] 다른 채널 이벤트가 현재 스트리머의 게임 이벤트로 전달되지 않는지 확인한다.
- [ ] 채팅 후원과 영상 후원을 각각 실제로 1회 이상 수신한다.

### 3. 후원 효과와 정확히 한 번 적용

- [ ] 마을과 던전에서 1,000/3,000/5,000/10,000원 구간을 각각 시험하고 규칙·효과·오버레이가 일치하는지 확인한다.
- [ ] 최소 금액 미만, 잘못된 금액, 알 수 없는 이벤트는 게임 효과가 발생하지 않는지 확인한다.
- [ ] 로딩, 장면 전환, 일시정지, 대화, 컷신 중 후원이 대기하고 안전한 시점에 적용되는지 확인한다.
- [ ] 던전 체력이 0.5 하트일 때 피해 후원으로 플레이어가 즉사하지 않는지 확인한다.
- [ ] 복합 버프/디버프가 같은 시점에 시작하고, 게임 일시정지 동안 효과와 오버레이 시간이 함께 멈추는지 확인한다.
- [ ] 후원 카드 여러 건이 FIFO로 한 장씩 표시되고 같은 카드가 중복 표시되지 않는지 확인한다.
- [ ] 게임이 꺼진 동안 Companion이 실제 후원을 받으면 `DONATION_OUTBOX`가 증가하고, 게임 연결 뒤 정확히 한 번 적용된 후 0이 되는지 확인한다.
- [ ] Companion을 outbox 저장 직후/전송 직후/ACK 직전에 종료하고 재시작해도 효과가 한 번만 적용되는지 확인한다.
- [ ] Mod가 효과 적용 후 결과 전송에 실패한 상황을 만들고, 재전송 시 저장된 결과만 반환하며 효과가 반복되지 않는지 확인한다.
- [ ] 게임을 `PENDING` 상태에서 종료한 경우 재시작 후 한 번 적용되는지 확인한다.
- [ ] 게임을 `APPLYING` 상태에서 강제 종료한 경우 `UNCERTAIN`으로 기록되고 자동 재적용하지 않는지 확인한다. 이 경우 효과 적용 여부를 운영자가 수동 판정할 절차도 정한다.
- [ ] 동일한 내부 request ID를 두 번 보내도 게임 효과는 한 번만 적용되는지 확인한다.
- [ ] `status`의 `DONATION_OUTBOX`, `DONATION_PENDING`, 게임 로그의 receipt 상태가 최종적으로 정상 정리되는지 확인한다.

### 4. 시청자별 신도 세대·부활·저장 호환성

- [ ] 첫 신도 이름에는 `1세`가 붙지 않고, 두 번째부터 `닉네임 2세`, `닉네임 3세`로 생성되는지 확인한다.
- [ ] 살아 있거나 실종·감금·원정 중인 신도가 있으면 새 신도 생성이 막히는지 확인한다.
- [ ] 사망이 확정되면 다음 세대 외형 설정과 생성 권한이 열리는지 확인한다.
- [ ] 사망한 시청자 연동 신도가 게임 부활식 후보에서 제외되지 않는지 확인한다.
- [ ] 이전 세대가 부활해도 이미 설정한 다음 세대의 래플 생성 권한과 외형이 취소되거나 덮어써지지 않는지 확인한다.
- [ ] 생성됨/사망함/부활함 이벤트, 생존 기간, 사망 원인, 세대별 외형이 올바른 신도 기록에 남는지 확인한다.
- [ ] 기존 RC 저장, 새 저장, 여러 저장 슬롯 전환 후 세대 번호·생존 상태·외형 이력이 섞이지 않는지 확인한다.
- [ ] 저장 도중 종료, 누락 필드, 손상된 로컬 이력 파일에서 안전하게 실패하거나 복구 파일을 남기는지 확인한다.

### 5. 시청자 웹·래플 최종 외형

- [ ] 로그인한 시청자가 생성 가능한 다음 세대와 `신도 이름 : 닉네임 O세` 표시를 정확히 보는지 확인한다.
- [ ] 시청자가 래플 전까지 외형을 여러 번 바꾼 뒤, 당첨 시 서버에 마지막으로 저장된 값으로 게임 신도가 생성되는지 확인한다.
- [ ] 당첨자 확정 시 이름과 외형이 게임의 현재 신도에 함께 실시간 반영되는지 확인한다.
- [ ] 과거 세대 외형을 조회·복사해 현재 설정으로 붙여넣어도 과거 기록 자체는 변경되지 않는지 확인한다.
- [ ] 외형/색상/변형 각 탭의 항목 미리보기와 조립된 정적 미리보기가 실제 게임 외형과 일치하는지 확인한다.
- [ ] `Follower.atlas.bytes`, `Follower.skel.bytes`, `Follower.png`가 웹 배포에 포함되고 CloudFront에서 올바른 MIME/CORS/캐시 정책으로 내려오는지 확인한다.
- [ ] 모바일과 데스크톱 브라우저에서 큰 `Follower.png` 다운로드 시간과 메모리 사용량을 확인한다.

## P1 — 회귀 및 복원력 테스트

- [ ] 자동 래플 참가, 당첨, 초록색 `Chzzk` 이름표와 기존 외형 카탈로그 동기화를 재시험한다.
- [ ] OBS 오버레이 1920x1080에서 후원 카드 480px/좌측 상단 18px, 버프 좌측 정렬, 문서 버전 자동 갱신을 확인한다.
- [ ] 네트워크 단절, CHZZK 429, 게임 소켓 재연결, Companion 재시작을 반복해 이벤트 유실·중복이 없는지 확인한다.
- [ ] 후원 32건 이상 연속 수신 시 outbox 처리량, 오버레이 큐, 게임 프레임 정지 여부를 확인한다.
- [ ] `support` ZIP에 토큰, 설정, 닉네임/후원 메시지, 신도 외형 데이터, outbox/receipt 내용이 포함되지 않는지 직접 열어 확인한다.
- [ ] Companion 로그 순환과 손상 outbox 격리, Mod receipt 손상 격리 로그가 개인정보를 노출하지 않는지 확인한다.

## P2 — 운영·배포 준비

- [ ] 최종 빌드는 커밋 또는 태그가 확정된 깨끗한 작업 트리에서 다시 생성하고 최종 ZIP SHA-256을 릴리스 기록에 남긴다.
- [ ] CDN 업로드 후 원격 파일 해시가 `SHA256SUMS.txt` 및 매니페스트와 일치하는지 확인한다.
- [ ] 잘못된 SHA-256, 다운로드 중 인터넷 차단, 부분 ZIP에서 설치기가 안전하게 중단되고 기존 설치를 손상하지 않는지 확인한다.
- [ ] 이전 배포본과 롤백용 구성요소를 보관하고 장애 시 복귀 절차를 시험한다.
- [ ] 설치기/Companion 코드 서명 도입 여부와 인증서 보관·서명 자동화 정책을 결정한다.
- [ ] 실제 방송 30~60분 soak test 후 CPU, 메모리, 로그 증가량, outbox/receipt 잔존 건수를 기록한다.

## 배포 승인 기준

- P0 항목을 모두 통과해야 외부 배포 가능하다.
- 실패는 현재 변경으로 인한 회귀, 기존 문제, 환경 문제, 간헐 문제로 구분해 기록한다.
- P1 실패는 영향 범위와 우회책을 명시해 배포 여부를 별도 판단한다.
- P2 미완료 항목은 운영 위험으로 릴리스 노트에 공개한다.
